## The publish-retry bug

Test: `GraphPublisher incremental cache > does not lose a failed publisher node`  
Symptom: expected `["n1"]`, received `["n1", "n2"]` on the retry flush.

### Root cause

`GraphPublisher` used one `#marked` set for two unrelated meanings:

1. state invalidation, which must propagate to downstream dependents; and
2. renderer publish retry, which must retry only the failed node while its cached patch is still valid.

After `n1`'s publish failed, retrying `n1` looked like a fresh upstream change, so the forward pass republished `n2` even though `n2` had already succeeded against an unchanged patch.

### Fix

Added a separate `#publishPending` set. State marks still propagate through `changed`; publish retries recompose and retry only the failed node without entering `changed`. Compose failures still block downstream and stay state-pending.

## Failure semantics, settled

The rule lives in the failure-semantics section of `docs/V4.3-GRAPH-CORRECTNESS-PLAN.md`:

- **Compose failure** produces no patch, so the node and its full downstream closure are blocked for the flush, the node stays state-pending, and the next flush republishes the node and its dependents.
- **Publish failure** means the patch is valid and only the paint failed, so dependents publish in the same flush and only the failed node retries later.
- Independent branches always continue; errors surface as one `AggregateError` after the pass.

### D3 reconciliation

`GraphPublisher.contract.test.js` D3 was authored in Phase 0, before the cache existed, and asserted the retry flush republished `["n2", "n3", "n4", "n5"]`. That contradicted its own earlier assertion, which already showed `n3`-`n5` publishing successfully in the failing flush off `n2`'s valid patch. It now asserts `["n2"]`. A stale expectation, not a weakened one: blocking that subtree would have contradicted the test's own title.

Two testing rules that are load-bearing, not style preferences:

1. **Never hand a graph test a fake object-literal track.** The original publisher tests did, and certified a publisher that could not publish dependents at all. Use `packages/core/src/__fixtures__/graphTracks.js`.
2. **Inject compose failures through the real plugin path** via `buildRealGraph(motion, { onCompose })`, so the error travels through `composePatch` as it would in production.

### Why the cross-flush property matters

Every pre-existing fuzz property flushed once from a cold cache, where everything recomposes anyway, so none of them could observe a stale cache. The new property warms the cache, drives random `progress()` changes over several rounds, and asserts that after each flush *every* node's last published patch equals a from-scratch compose. The invariant is global rather than scoped to the publish set, so a node that silently served a stale cached patch fails even though it never appeared in the publish set. It also uses no `markDirty()`, which means it covers the lifecycle-hook wiring an engine actually depends on.

Note that `GraphBinding` commits through `applyGraph`, which clears the cache and re-marks every track. Topology mutation therefore cannot produce a stale cache; only state mutation across warm flushes can. That is why the two new properties are split the way they are.

## Next work

Nothing is blocking. Remaining opportunities, in rough priority order:

1. Migrate any remaining app-level manual observation cleanup to `GraphBinding`.
2. Decide on a retry budget or backoff. A publish-pending node currently retries every flush forever, which is fine for a transient renderer fault and wasteful for a permanent one.
3. Consider a narrower `applyGraph`. Wiping the whole cache on every topology commit is correct but conservative; only the mutated node's downstream closure strictly needs invalidating. Worth doing only if a benchmark shows it matters.
4. Run `graphify update .`.

## Workflow rules

- Follow-up PRs target `v4.3`, not `master`.
- Wait for all five checks before merging. Roughly 40 seconds, closer to 90 now that the fuzz suite runs 500 seeds.
- If CI is red, preserve the unit-test failure log before diagnosing.
- Keep standalone mutual observation and per-call Track compose semantics unchanged.
- Do not add a Track cross-frame cache. Cross-flush caching belongs to GraphPublisher.
- Use real Track fixtures for graph tests, never fake object-literal tracks.
- When a test and the implementation disagree, decide which one encodes the intended contract before changing either.
