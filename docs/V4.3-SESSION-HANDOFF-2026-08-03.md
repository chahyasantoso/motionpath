## What the failure means

The test assumed that after `n1` publish fails, `n2` should be retried alone on the next flush. The current publisher intentionally treats a publish failure differently from a compose failure: the patch is valid, so downstream `n2` is allowed to publish in the same flush. Therefore `n2` remains marked only if its own publish failed, not merely because upstream `n1` publish failed.

The failure is likely in the test expectation, not automatically in the publisher. Do not weaken the implementation blindly. First decide and document the intended contract:

- **Current design:** compose failure blocks downstream; publish failure does not. Then the test should expect the second flush to publish `n1` only if `n1` was the sole pending retry. This requires checking whether `n2` was already successfully published during the first flush and clearing its pending state correctly.
- **Alternative stricter design:** any publish failure blocks downstream and retries the full downstream closure. This is simpler for renderer consistency but less independent and less parallel-friendly.

Recommended decision: keep the current split semantics. Renderer publish failure does not invalidate a valid composed patch for dependents, but the publisher must not republish a successfully published dependent on the next flush. Inspect `#marked`/changed propagation and add an explicit regression assertion for retry behavior.

## Immediate next task
