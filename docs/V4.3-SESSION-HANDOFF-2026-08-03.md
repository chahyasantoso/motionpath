## Failure diagnosed and fixed

Test: `GraphPublisher incremental cache > does not lose a failed publisher node`  
Original result: **69 passed, 1 failed; 376 passed, 1 failed**  
Observed mismatch: expected `["n1"]`, received `["n1", "n2"]` on the second flush.

### Root cause

`GraphPublisher` used one `#marked` set for two different meanings:

1. state invalidation, which should propagate to downstream dependents; and
2. renderer publish retry, which should retry only the failed node when its cached patch is still valid.

After `n1` publish failed, retrying `n1` on the next flush looked like a fresh upstream change, so the forward pass republished `n2` even though `n2` had already succeeded and its patch was unchanged.

### Fix

Added a separate `#publishPending` set. State marks still propagate through `changed`; publish retries recompose and retry only the failed node without adding it to `changed`. Compose failures still block downstream and remain state-pending for retry.

This preserves the intended contract:

- valid publish failure: downstream may publish in the same flush, only the failed node retries later;
- compose failure: downstream is blocked until the source composes successfully;
- independent branches continue when another branch fails.
